# Android: перевод на язык web v2 и тактильные компоненты — дизайн, 2026-11-13

Статус: поэтапная работа в `android-rebuild`. 2026-11-13 владелец одобрил общую
компоновку HTML каркаса/плеера и запросил полировку. Последним уточнением того же дня
он закрепил первоначальный **Dream как сырой, но в целом подходящий ориентир**;
детальная приёмка каждого экрана впереди (§6.6). Уточнения ниже имеют приоритет
над первоначальным решением о волне. Полный перенос экранов в Compose ещё впереди.
Связано: [`components-research.md`](components-research.md) (ресёрч и решения по витрине),
[`mocks/tactile-components/`](mocks/tactile-components/README.md) (витрина — источник поведения
компонентов), [`design-v2-requirements.md`](design-v2-requirements.md) (дизайн-код кратко).

## 1. Зачем

Android-приложение 2.0.5 последний раз менялось 2026-10-02 и сделано «как в v1». Web за октябрь
перешёл на язык v2: плеер «Кино» (10-04), «Разворот» (10-10), «Стена» и статистика (10-11),
переходы «фокусом» (10-11), настройки (10-14), «Кадр» (10-17), главная с небом и сферой,
ассистент вместо поиска. `design/code/roadmap.md` прямо откладывал Android: «follows later, from
the approved web screens». Это «позже» наступило.

Решения владельца в этом разговоре:
- телефон повторяет web **по устройству экранов**, не только по стилю; работа идёт **по этапам**;
- способ — **телефонный HTML-макет → «да» → перенос в Compose** внутри нынешнего приложения;
- seek плеера на телефоне — **разделы песни под единой непрерывной волной** (§6.4);
- APK этапа ставится **обновлением основного приложения сначала только на телефон владельца**; он
  тестирует полуготовое сам, другим — после его слова (§5.1);
- из витрины тактильных компонентов приняты 12 из 14 (таблица в §6); сценарий скачивания
  Richbox — только как идея, **Richbox внутри принятых шагов ассистента сохраняется**;
  листание обложки — переделать с физикой.

**Успех:** открывая приложение, владелец видит тот же продукт, что на web, только в руке: те же
экраны и движения, телефонная компоновка, точная вибрация на ключевых жестах, телефон не греется.
На каждом этапе у него на телефоне рабочий APK.

## 2. Цели, не-цели, анти-цели

**Цели**
1. Структура как у web: Главная (небо, сфера «Поток», быстрый поиск), Плеер «Кино», Библиотека
   «Стена» + «Разворот» + статистика, Артист «Кадр», Плейлист, Ассистент, Игра, Настройки,
   импорт/загрузка, вход и первый запуск.
2. Язык как у web: токены из `design/gen/android`, типографика (Geist / Noto Sans / JetBrains Mono),
   поверхности (glass редко, float, plate), «всё физично», смена страниц «фокусом».
3. Принятые компоненты из витрины на своих местах, вибрация одним словарём.
4. Приложение работает на каждом шаге: каждый этап — устанавливаемый APK.

**Не-цели**
- Windows-клиент, мобильный web (его закрывает приложение).
- Офлайн-скачивания (будущее; тогда же — сценарий скачивания Richbox на телефоне).
- Кроссфейд (владелец 2026-10-13: «если на андроиде два плеера — не надо»).
- Desktop-вещи: наклон за курсором, hover, раскладки 14/16/32″, спектр (на телефоне его нет по
  `screens/player.md`).
- Админка на телефоне (на web она есть в острове у владельца) — *моё решение*, вернём, если попросит.

**Анти-цели** (провал, даже если «работает»)
- Потерять то, что есть только в Android: Android Auto, виджеты Glance, «Слушать на…» и плашка
  «Играет на другом устройстве», уведомление/медиасессия, «Поток» в одно касание.
- Перенести desktop-раскладку буквально: на телефоне один экран без прокрутки, второстепенное — в шитах.
- Что-то крутится в покое, телефон греется, кадры рвутся (Pixel 9 Pro — 120 Гц, цель — частота экрана).
- Вибрация на каждый тап; отрисованный глянец, пластиковое 3D.

## 3. Ограничения

- **Mock first:** ни один экран не собирается и не перекрашивается до «да» владельца на телефонном макете.
- **Prod только на чтение.** Деплой, миграции, бэкфиллы — по явному «да». Web-build в задеплоенном
  checkout не запускать.
- **GPU — prod и llama-server.** Эмулятор (`tools/android/emu.sh`, Docker) и тесты — на CPU.
- Снимки реальной библиотеки — только `/mnt/data/musix-snapshots/`.
- Токены правятся только в `design/tokens/*.json` → `make design`; `design/gen/*` руками не трогать.
- Код, комментарии, коммиты — на английском; UI и документация — на русском.
- Стек: AGP 9.4.1, Kotlin 2.4.20, Compose BOM 2026.09.00, Hilt, Navigation 2.10 (type-safe
  `composable<…Dest>`), Media3 1.11, Glance 1.2, Coil 3, Roborazzi 1.76, `minSdk 24`, `targetSdk 36`.
- Сборка на сервере: `make android` (`assembleDebug`), `make android-check` (unit + Roborazzi).
  `versionCode` и `versionName` поднимаются вместе на каждый выданный APK.

## 4. Подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| **А (выбран)** | Телефонный HTML-макет из web-эталона → «да» → Compose, экран за экраном, внутри нынешнего приложения | быстрые круги правок, владелец трогает макет с телефона (как витрину); эталон `design/reference/<screen>/` уже есть, макет — адаптация; данные и плеер не трогаются | раскладка делается дважды; физика в браузере ≠ Compose → жесты окончательно принимаются в APK |
| Б | Макет сразу в Compose (debug-APK с переключателем вариантов) | нет переноса, настоящие пружины и вибрация | круг правок = сборка + установка; код макета норовит остаться в продукте |
| В | Новое приложение рядом | чистый лист | месяцы со старым приложением, пересадка Auto/виджетов, выпуск разом |

Владелец выбрал **А** 2026-11-13.

## 5. Как устроена работа

### 5.1 Рутина одного экрана (телефон)

Общий Dream сначала сохраняется как неизменный черновой ориентир, отдельно от
текущей версии. Исправления общей типографики и пропущенных принятых компонентов
не считаются приёмкой всех показанных экранов. Первый следующий подробный разбор —
главная, затем этапы таблицы ниже; перенос каждого экрана следует его отдельному «да».

1. **Назвать экран:** состояния (пусто, загрузка, ошибка, длинный текст, 1 и 1000 элементов),
   шиты, входы и выходы — по web-таблице в `roadmap.md`.
2. **Макет:** один HTML-файл (всё встроено, как `tactile-components.html`), собранный из
   `design/reference/<screen>/` (его CSS, разметка, `bake.py` для ассетов) и перекомпонованный под
   телефон. 1–2 варианта (язык уже принят, три не нужны). Размеры: **360×780** (пол), **412×915**
   (Pixel 9 Pro владельца), **448×998** (крупный) — переключатель в макете. Данные — снимок из
   `/mnt/data/musix-snapshots/`. Отдаётся файлом и по dev-адресу Tailscale.
3. **Реакция владельца** → `design/code/preferences.md` в тот же день.
4. **«Да»** → исходники в `design/reference/<screen>/phone/`, правила — раздел `## Phone` в
   `design/code/screens/<screen>.md` (как уже есть у плеера).
5. **Сборка в Compose** (§5.3), проверка (§5.5). APK — **release-сборка с релизным ключом**
   (`/mnt/data/android/keys`), ставится обновлением основного приложения на телефон владельца по adb
   (не через публикацию). Он живёт с полуготовым приложением и тестирует сам; жесты с физикой
   (перелёт плеера, листание обложки, перетаскивание очереди) принимает в нём же.
6. **Публикация APK для остальных** (существующий publish-apk) — только по его слову.

### 5.3 Код

- **Внутри нынешнего проекта.** `core/data`, `core/player`, `core/network`, `core/database` и
  Auto/виджеты/handoff не переписываются; меняются интерфейсы `feature/*` и `app/ui` (навигация,
  оболочка). Маршруты `composable<…Dest>` сохраняются, добавляются недостающие (`PlayerDest` как
  экран, `AlbumDest` → «Разворот», `QuickSearch`).
- **Старое уходит, когда последний экран перестал его использовать** (например, `Relief`, `BlurHash`,
  v1-`Backdrop`): без параллельных «v1/v2» версий одного компонента.
- **Экраны без web-эталона** (вход, первый запуск, общая игра; загрузка и импорт на web — окна
  библиотеки): один раунд макетов сразу на web и телефон, как у плейлиста; макет телефона идёт первым, web
  следует ему (*моё решение*).
- **Ветка:** новый worktree от `design-refresh` (там самый свежий web и дизайн-код), например
  `/mnt/data/android-rebuild`, ветка `android-rebuild` (*моё решение*). В `design-refresh` сейчас ~20 незакоммиченных файлов (главная, `Sky.tsx`,
  `Stats.tsx`, `setup.tsx`, сервер): worktree создаётся после того, как эта работа закоммичена; макеты
  главной, статистики и первого запуска опираются на неё.
- **Новое в `core/designsystem`:** `Haptics`, `Motion` (пружины), `PageChange`, `Sheet`, `ToastHost`,
  `WavySeek`, `MorphIcon`, `MorphButton`, `EventBanner` (JoiPro), `FluidHighlight`, `Steps`,
  `MultiStep`, `CodeField` (Password), `SparkBurst`. Каждый — с Roborazzi-снимком в
  `GalleryScreenshots` (галерея компонентов на Android).

### 5.4 Этап 0 подробно

- `make design`, сверить `MusixTheme.kt` с web-токенами (темы обе, звуковая триада).
- **Вибрация** (`core/designsystem/Haptics.kt`): 9 видов ↔ `HapticFeedbackType` (`SegmentTick`,
  `ToggleOn/Off`, `GestureThresholdActivate/Deactivate`, `LongPress`, `GestureEnd`, `Confirm`,
  `Reject`); тики не чаще 45 мс, один вид не чаще 120 мс; глобальный выключатель в настройках
  (DataStore); тишина для обычных тапов, листания, ввода и событий без пальца. На API < 30, где
  нет `Confirm/Reject`, — ближайшие `performHapticFeedback`-константы.
- **Движение:** пружины с теми же жёсткостью/затуханием, что `--spring`/`--snap` web (числа — из
  `motion-and-performance.md`); смена страниц «фокусом»: fade + размытие 8 px на API 31+
  (`RenderEffect`), на 24–30 — только fade.
- **Зависимости:** Haze 2.0.1 → 2.1 (`haze-glass`), `androidx.graphics:graphics-shapes` 1.1.0
  (morph), `sh.calvin.reorderable` 3.1.0. Волнистый seek — **своя реализация** (Canvas-путь,
  фаза анимируется в `graphicsLayer`), не M3 1.5.0-rc01 (*моё решение*: RC и чужой вид).
- **Замеры:** модуль `android/benchmark` (Macrobenchmark) — открыть плеер, листать «Стену»,
  перелёт мини-плеера; `FrameTimingMetric` (p95 ≤ периода кадра 120 Гц) и «в покое 0 кадров».
- **Дизайн-код:** записать в `design/code` — волнистый seek **только на телефоне** (раздел `## Phone` в
  `screens/player.md`; на web линия не меняется — над ней спектр); словарь
  вибрации в `motion-and-performance.md`; новые компоненты в `components.md`.

### 5.5 Проверка каждого этапа

`make android-check` (unit + Roborazzi), release-сборка с R8 (минификация не ломает экран), smoke
Android Auto, виджетов Glance и «Слушать на…» — **на каждом этапе**, раз приложение основное; прогон на эмуляторе на трёх размерах, Macrobenchmark
(§5.4), 10 минут воспроизведения с открытым плеером — без троттлинга (`dumpsys thermalservice`)
и без заметного расхода в покое, проверка вибрации на телефоне владельца. Замеры кадров и нагрева — **только
  на его Pixel 9 Pro**, подключённом по USB к его ПК (так уже отлаживали вибрацию 2026-11-13; adb есть в
  `%LOCALAPPDATA%\Android\Sdk`); эмулятор в Docker на CPU — только функциональные проверки и снимки
  (*моё решение*) (при выключенном
«Не беспокоить» нативная вибрация и так работает — см. §6.3). Затем APK владельцу.

### 6.1 Листание обложки — новая физика

Владелец: «странно выкидывает альбом, не физично». Требования к макету и Compose:
обложка идёт за пальцем 1:1; за краем — сопротивление (резинка); решение «сменить / вернуть» —
по смещению **и скорости** (fling); уход и возврат — пружина, продолжающая скорость пальца, без
постоянной длительности; следующая обложка въезжает от края синхронно (её видно во время жеста);
отпустил до порога — пружиной на место. Сначала — карточка с двумя-тремя вариантами пружины в
витрине (HTML), окончательно — в APK.

### 6.2 Перетекающая кнопка (идея Richbox)

Одна кнопка плавно перетекает состояниями: «В очередь» → «В очереди ✓» (→ «Убрать»), «В плейлист»
→ выбор → «Добавлено ✓». Форма, ширина и иконка меняются одной пружиной; текст — кроссфейдом.
Где: строка трека, плеер, «Разворот». Состояние «в очереди» — клиентское (очередь в `core/player`),
сервер не нужен. Сам Richbox (статус скачивания) — когда появятся офлайн-скачивания; на web —
возможно в импорте из Яндекс Музыки (вне этого документа).

Это ограничение относится к **скачиванию**, а не ко всем применениям индикатора.
Витрина «Шаги ассистента» уже использует `createRichbox(..., 16, 'waiting')` и
переход к `done`. Этот компонент входит в принятые Steps и берётся как есть.
В телефонном HTML добавлены ошибка, отмена и повтор; скрытый индикатор не крутится.

### 6.3 Вибрация и «Не беспокоить»

Проверено 2026-11-13 на Pixel 9 Pro владельца: при «Время сна»/«Не беспокоить» Android глушит
`navigator.vibrate` из Chrome, но не `performHapticFeedback`. Нативный слой (`HapticFeedbackType`)
этим не страдает; в настройках приложения — свой выключатель вибрации.

### 6.4 Seek плеера: блоки и волна

Уточнение владельца после просмотра HTML, 2026-11-13: волна, разбитая между блоками,
не выглядит целостной. **Сыгранная часть — одна непрерывная волна с общей фазой**,
пересекающая границы разделов. Блоки под ней сохраняют зазор 3 px, яркость припевов,
название текущего раздела и точки моментов. На паузе сыгранная часть выпрямляется.
Нет данных о разделах — одна длинная линия. Это уточнение заменяет первоначальное
«в зазоре не рисуется». WEB seek не меняется; данные разделов и моментов те же.

### 6.5 Полировка первого телефонного HTML — 2026-11-13

- Общая компоновка каркаса/«Кино» понравилась; глобальная переработка не требуется.
- Play/pause полного плеера — только на обложке, с подсказкой первого использования.
  Мини-плеер сохраняет свою кнопку, когда полный плеер закрыт.
- Мягкая пружина остаётся основой; добавить ощущение веса. В HTML по умолчанию
  stiffness 240, damping 25, mass 1.15, небольшой подъём/наклон и податливость при нажатии.
- При next/previous приехавшая карточка остаётся той же карточкой. Изображение,
  blur и значок не подменяются в конце движения; новая команда продолжает текущую скорость.
- Владелец подтвердил **Haze / haze-glass 2.1**. Android `LiquidGlass` использует
  библиотечный `GlassStyle.clear` и отдельный `hazeSource`; HTML показывает CSS-аналог,
  не исполнение Android-шейдера в браузере. Принятые файлы `vendor/` не меняются.

## 7. Серверная работа

**Pairing (вход по коду с сайта), этап 10.** На web в настройках («Устройства» / Android-баннер)
владелец нажимает «Войти на телефоне» → сервер выдаёт 6-значный код на 5 минут, одноразовый,
привязанный к аккаунту; телефон после «Где ваш сервер?» вводит код → получает те же токены, что при
логине, и появляется в `/devices`. Неверный код — `Reject`, лимит попыток. Эндпоинты, схема и миграция
— в отдельной серверной спеке; контракт — через `make openapi codegen`. Миграция и выкладка — по «да».

**Web-часть pairing входит в этот план:** кнопка «Войти на телефоне» в Android-баннере web-настроек
(«Устройства») и окно с кодом. Сервер и кнопка выходят вместе одним изменением. Ветки `design-refresh`
и `v2` разошлись (2 и 6 коммитов), поэтому ветку для этого изменения выбираем с владельцем на этапе 10
(*моё решение — отложить выбор*).

Других серверных изменений этапы 0–9 не требуют (*проверить при макете каждого экрана*: данные
web-экранов уже отдаются API, которым пользуется web).
