# v2 phase 2 — exit bench (spec §9), 2026-09-30

`tools/bench/v2/phase2.py` and `ingest.py` on the dev stack (home box, 12 cores, CPU-only
ml — the GPU is prod's), next to v1 prod (load average ≈ 4 before the run). Raw numbers:
`2026-09-30-v2-phase2.json`.

## Setup

- **Data.** The 2026-09-29 prod snapshot loaded into `musix_snap`: 5 real
  accounts, their libraries (50–6000 tracks), listening histories, the promoted ranker
  (v1 features, GAUC 0.786). Queries: the gate fixtures (lyric lines, titles, sound
  prompts), which stay with the snapshot, out of git.
- **Stack.** api-snap: uvicorn, 4 workers (spec §1), direct on :18010 (no nginx in front of
  the snapshot api). ml: one CPU process, priority executor. Postgres 18, Qdrant 1.18.
- **Load.** 20 clients per route spread over the accounts. *Paced*: each client waits 1 s
  between requests (10 s for all-sections search) — 20 people using the app, still
  hundreds of times more often than a listener asks for the next «Поток» chunk. *Stress*:
  closed loop, no think time (the phase 1 model), for scale. The bench's own served-today
  history is cleared before each «Поток» scenario.

**`/stream/next` under stress** misses the budget: a chunk costs ≈ 50 ms of Python per
request (state load, the five candidate sources, 27 features over ~550 candidates, the
ranker, the policy, reasons, the decision log), so 4 workers saturate near 80–140 rps and
20 clients without think time queue behind each other. Fixed on the way: LightGBM served
on one thread (OpenMP's pool cost 0.8–13 ms a call once idle between awaits, against a
steady 2.7 ms; the stress throughput went 63 → 82–139 rps, p95 912 → 381–495 ms). The
paced run — the budget's "20 users" — holds p95 < 150.

**Search on the CPU ml.** A query encode is 67 ms dense and 60 ms CLAP here (spec §9
assumes ~20 ms on the GPU); all-sections search is therefore paced to 2 rps, which the one
CPU ml process sustains. On prod's GPU the same path is expected well under budget.

## Ingest (all intelligence but the LLM enrichment)

A real folder the dev DB had never seen, 39 files: scan → media
(renditions, covers) → intel (online lyrics, CLAP audio + chunks, dense text, axes) —
**279 s wall-clock, 7.15 s per file, 0 failed**; extrapolated to a 6000-track
library ≈ **11.9 h on this CPU**. v1's full-library wall-clock is not in the
phase 0 baseline, so the "≤ v1" check is open: v1 embedded text on the GPU and CLAP on the
CPU (v1 CLAUDE.md), v2's dev ml does both on the CPU. Phase 3 copies the snapshot's vectors
(no re-embed), so this rate bounds new uploads, not the migration.
